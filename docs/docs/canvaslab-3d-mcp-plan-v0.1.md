# CanvasLab 3D MCP：参考图生成可交互三维网页规划

日期：2026-09-12

状态：设计提案，尚未实现、安装或部署。文中的工具、路径、门槛均为拟议方案。

暂定产品名：CanvasLab 3D；首版协议：`canvaslab-scene-v1`。

## 1. 结论与第一版目标

新增独立的 3D MCP，与现有 CanvasLab 二维拆图／网页还原并行。首版以“青崖渡”这样的风格化水乡、建筑微缩景观、小型展台为目标：输入参考图，输出可以旋转、缩放、移动指定物件、播放简单动画的 Three.js 网页工程。

核心改进不是把“看图写 JS”包成一个工具，而是把模型的决定变成可校验的场景配置，并让每轮结果接受原图对照和三维交互验证。

- 模型负责理解参考图、提出物件和材质方案、观察差异并修改参数。
- MCP 负责保存证据、验证配置、生成固定运行时工程、调度截图与测试、记录版本和验收状态。
- 浏览器负责实时渲染和交互；首版无需大型图生 3D 模型，也不以购买新显卡为前提。
- 这是视觉参考驱动的三维重建，不是从单图恢复真实尺寸、隐藏表面和物理材质的测量系统。

第一版默认做真正有体积的风格化 3D，明确声明允许观察的角度范围。2.5D 图层视差可作为后续独立模式，不能拿来冒充完整三维重建。

## 3. 用户流程与系统分工

```text
用户原图 + 要求（能动哪些物件、允许转多少角度）
  → 保存原图与版本，模型建立对象清单和测量标注
  → 校验 scene-plan，先生成灰模并匹配参考相机
  → 模型检查构图，再补几何细节、颜色、材质和光照
  → MCP 用固定运行时生成独立 Three.js 工程
  → 捕获参考视角 + 侧视角 + 移动端 + 交互证据
  → 数值检查 + 模型逐区域视觉审查
  → 不通过：修改场景参数，生成新构建并重新捕获
  → 通过：交付网页工程、审计报告和有范围说明的证书
```

首版由当前调用 MCP 的模型执行看图与修正。MCP 不会因为网站上有“开始”按钮就自动获得 Codex 会话或模型调用额度。未来如果需要无人值守生成，再增加单独的模型服务适配器、凭据、费用和任务权限配置；本轮不纳入。

用户以后可直接说：“用 CanvasLab 3D 按这张图做一个场景，船能行驶和拖动，保持原图构图。”工具返回明确的 `next_action`，模型按合同推进，而不是重新自由设计。

采用同仓库、独立模块、独立服务；先不拆第二个 Git 仓库。这样能复用经验和测试，同时保持两条生成链路分开发布。

拟议目录：

```text
server3d/

  jobs.py               # 持久化状态、幂等、版本、配额
  scene_schema.py       # 对象、相机、材质、交互、目标标注的校验
  analysis.py           # 场景标注与可选视觉能力适配
  builder.py            # 配置 → 固定模板与资产清单
  audit.py              # 局部视觉、三维结构、证据与完成条件
  tests/
runtime3d/
  src/primitives/       # 受控的参数化组件库
  src/scene/            # 场景加载、相机、材质、动画、交互
  src/capture/          # 固定状态、对象 ID、深度与测量接口
  package.json          # 自己的依赖和锁文件
scripts3d/              # 本地原图上传、下载、预览与捕获入口
benchmarks3d/           # 固定原图、人工标注、正例与失败样本
ops3d/                 # 独立服务、发布、校验、回滚

```

- 拟议服务端根目录 `/srv/canvaslab-3d/`；MCP 路径 `/mcp-3d`，不改变现有 `/mcp`。实际端口在实施前检查占用。
- 数据目录、虚拟环境、密钥、队列、日志、保留策略与二维隔离。`generated3d` 不使用其他任务的入口文件，不覆盖 `src/main.tsx` 或 `D:/codex/pve`。
- 捕获 worker 与 API/MCP 分进程运行。首版允许独立机器提供渲染 worker，不要求 Tesla 服务器同时承担浏览器渲染。
- M1 就需有最小 worker：登记设备和能力、鉴权领取指定构建任务、下载并验证资产、运行浏览器、回传证据，以及任务超时／取消。首台正式捕获设备在 M0 确认；只有 CPU 协调服务启动不算闭环就绪。
- GPU 分割是可选适配器；如启用，要与现有 GPU 任务统一限流或串行调度，不能为 3D 无限制重复加载一套模型。
- Three.js 运行时采用本地打包、锁版本的依赖，不依赖临时 CDN。当前官方 `WebGLRenderer` 使用 WebGL 2，目标浏览器需做能力检查；不支持时说明原因并显示标注清楚的静态预览。[Three.js 文档](https://threejs.org/docs/pages/WebGLRenderer.html)

## 5. 场景合同：不让生成模型随意发挥

### 两份分开的数据

1. `reference-annotations.json`：从原图得到的二维目标；包含原图摘要、场景裁剪框、物件框、轮廓、关键点、遮挡关系、显著性、置信度和证据来源。
2. `scene-plan.json`：拟合上述目标的三维方案；包含对象、父子关系、几何参数、相机、材质、灯光、交互和能力范围。

目标标注不能取自生成模型的渲染结果，否则“渲染结果和自己的框一致”会被误认为还原成功。模型提出的原图标注也不是测量真值：保留置信度与覆盖图，重要对象要逐项核对；基准集使用独立人工标注。变更目标标注必须留理由和新版本，不能为通过审计偷偷移动目标。

### 必需字段

| 字段 | 约束 |
|---|---|
| `schema_version / contract_version` | 独立的 3D 版本；不改二维 manifest 的版本 |
| `source_sha256 / annotation_revision` | 固定原图和审计目标；原图永远保留原生分辨率 |
| `reference_frame` | 原图尺寸、场景区域、坐标映射；页面文字与外框另计，不能拿场景截图比较整张网页 |
| `coordinate_system` | 右手系、Y 向上、明确相机前向；默认相对单位，没有标尺就不能声称厘米级尺寸 |
| `reference_camera` | 正交或透视、位置、朝向、投影参数、取景框；相机与画布比例绑定 |
| `objects[]` | 稳定 `object_id`、父 ID、角色、原图区域、几何类型、参数、位置、四元数旋转、缩放 |
| `materials / lights` | 调色板、纹理资产摘要、材质参数、灯光、曝光和色彩配置 |
| `constraints` | 接触面、物件相对大小、前后遮挡、允许相交的连接、禁止穿插的对象对 |
| `interactions` | 按对象 ID 声明拖动区域、暂停／继续、复位、动画路径、键盘和触屏行为 |
| `view_envelope` | 允许的水平／俯仰角范围，哪些角度已有参考图，哪些属于推断 |
| `reconstruction_method` | `procedural_mesh`、以后支持的 `imported_mesh`、`billboard` 等，不能混淆 |
| `assumptions / unsupported_features` | 隐藏结构、简化人物、未完成的材质或功能明确列出 |
| `seed / quality_profile` | 固定随机种子、性能预算、验收配置版本 |

校验器拒绝未知字段、无效数值、循环父子关系、外部任意资源路径、不支持的组件、超预算几何和不存在的交互目标。运行时不执行配置中的 JS、表达式字符串或任意着色器代码；自定义组件需要走受审查的组件库更新。

修改使用 `base_revision` 乐观锁，明确区分 `analysis_revision` 与 `plan_revision`。场景校验成功后持久化不可变计划，返回 `plan_id`、`plan_revision`、`plan_digest` 和绑定的 `annotation_revision`；无效计划不进入可构建版本。构建接受已保存的计划 ID，不依赖一个无法还原配置的摘要。每次构建保存不可变配置与资产哈希，并在入队时锁定生成器版本；旧版本可回看，新构建不能复用旧审计结果。无需要求模型永远写相同 JS，只要求它改受控参数，由同一生成器产生可追踪工程。

## 6. 首版组件库和还原顺序

### 参数化组件

基础：盒体、柱体、椭球、截面拉伸、有限截面的曲面／船壳、曲线路径、地面和水面。组合：房屋、瓦顶、窗框、木梁、栏杆、石岸、木板码头、船、箱子、简单树木与灯笼。

静态装饰可以合批或实例化，但必须保留逻辑对象到实例／网格的映射。船和可拖物件保持独立变换节点。对象 ID 不能因合批而丢失，否则选择、局部审计和导出无法对应。

参考水乡已有的规则提炼为参数，不把固定坐标、文案、船数量、水道方向写死。随机种子由场景 seed 和稳定对象 ID 派生，避免插入一棵树导致后续所有对象随机外观改变。动画采用可设置时间的函数；水波、尾波、随机分布和灯光均可被重置到固定状态；依赖历史的效果需从初始状态固定步进重放。

网页操作按钮和说明使用真实 HTML；建筑招牌可以是文字纹理，但需保留可编辑文字源和字体资产，在报告中说明不是 HTML。捕获时等待字体载入后再绘制纹理，避免截图时字形发生漂移。

### 还原迭代顺序

1. 区分原图中的页面 UI、三维场景区域和装饰背景，避免把标题或边框建成景物。
2. 先做整体轮廓与灰模，比较正交／透视候选，拟合相机、取景和主要对象大小。
3. 校正对象位置和遮挡，再补屋顶曲线、船壳、窗格等决定辨识度的细节。
4. 最后调材质、纹理、光照和氛围，再加动画和可操作 UI。
5. 修正记录必须说明“哪个对象、哪个参数、对应原图哪里”；不能用增加装饰掩盖比例错误。

相机和尺寸存在多解，首版采用模型建议加有限范围搜索，不承诺自动求得唯一相机或物理尺度。重要轮廓没有合适组件时返回 `unsupported_geometry`，不能静默替换成一张贴图后签发三维完成证书。

旋转缩放可基于 `OrbitControls`，拾取可基于 `Raycaster`；MCP 仍须实现拖物件与拖镜头的互斥、边界和复位逻辑。[OrbitControls](https://threejs.org/docs/pages/OrbitControls.html)、[Raycaster](https://threejs.org/docs/pages/Raycaster.html)

## 7. 拟议 MCP 工具接口

以下是首版设计名称，不代表本机现在已有这些工具。使用输入／输出 schema 和结构化结果，错误要包含可行动的原因。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

| 工具 | 主要输入 | 输出／作用 |
|---|---|---|
| `scene_runtime_status` | 无 | 服务、生成器、合同、worker、可选 GPU 后端版本和能力 |
| `submit_scene_reference` | 已上传资产 ID、需求、模式、幂等键 | `job_id`、原图尺寸／哈希、下一步；不强制先走 UI 拆图 |
| `get_scene_job` | `job_id` | 阶段、当前构建、历史、错误、`next_action`、完成状态 |
| `save_scene_analysis` | 原图标注、置信度、假设、基础版本 | 校验后的分析版本和原图标注覆盖图 |
| `validate_scene_plan` | 场景配置、分析版本、基础计划版本 | 错误／警告、支持范围、预算；成功后保存计划并返回 ID／版本／摘要 |
| `build_threejs_scene` | 已保存的计划 ID／版本、幂等键 | 异步构建 ID、锁定的生成器版本、固定模板工程、签名资产清单 |
| `capture_scene_views` | `build_id`、已登记的视角与设备配置 | 由捕获 worker 生成的 `capture_id`、截图、对象 ID／深度、测量记录 |
| `audit_scene_views` | `capture_id`、结构化模型发现、前次审计 ID | 局部指标、阻断项、建议参数方向、下一轮要求 |
| `run_scene_interaction_tests` | `build_id`、合同测试集版本 | 实际浏览器事件、前后状态和截图证据 |
| `run_scene_performance_tests` | `build_id`、已登记设备 ID、基准版本 | 预热后计时记录、帧时分布、资源预算与性能证据 ID |
| `complete_scene_review` | 同一构建的视觉／交互／性能证据 ID | 通过或缺失项；只在所有必需条件满足时签发 |
| `export_scene_project` | `build_id`、格式 | 源码和可部署网页 ZIP；GLB 为后续有损导出能力 |
| `cancel_scene_job` | `job_id` | 中止排队或正在进行的可取消阶段，保留已有证据 |

原图由本地上传脚本直接读取原始字节，通过受限上传 API 获得资产 ID，不让远端读取本机路径，不通过缩略图规避大小限制。产物返回资源链接和摘要，不把大文件塞进文本结果。

普通任务状态使用持久化轮询，不依赖某个客户端独有的长任务扩展。选择兼容的 MCP SDK 并做真实客户端协议协商测试；不要把应用层 `capture_id` 当作 MCP 传输会话。Streamable HTTP 行为有版本差异，依官方协议和实际客户端测试锁定。[传输规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)

状态主线：`reference_ready → analysis_ready → plan_validated → building → built → captured → needs_revision / visual_accepted → complete`。模型尚未审查时为 `awaiting_model_review`，不是失败。资源不足、缺少可信捕获、能力不支持分别返回原因；发生相同无改动重试不自动无限循环。

暂定最多 4 轮自动修正；连续 2 轮关键指标不改善或来回振荡时输出阻断报告、保留可预览版本，不宣称完成。继续增加轮数或缩减支持范围必须明确记录。

## 8. 3D 审计：分别证明相似、立体和可用

### A. 可重复且可追踪的捕获

- 只捕获登记的 `build_id` 对应工程，不接受 MCP 任意传入网页 URL 后让服务器浏览内网。
- 固定原生参考尺寸、DPR、参考相机、种子、动画时间、光照、曝光、色彩空间；等待字体、纹理和 shader 就绪。
- 不仅禁用 CSS 动画，还必须冻结 Three.js 时钟、控制器阻尼、水波、船只、尾波等状态。
- worker 校验浏览器实际加载的 JS、配置、纹理与资产字节摘要，而非只检查本地文件或页面自报的版本标记。
- 一次捕获同时产出 beauty 图、对象 ID 图、深度／轮廓和对象投影数据。原图、分析、构建、相机、时间、浏览器／渲染环境、文件摘要和随机 nonce 共同绑定到捕获记录。
- 密钥在 worker／服务端，不能进页面。只上传手写 `observed.json`、`build_verified=true` 或一张旧截图不能获得正式证据。
- 首版正式验收由受管理、经过鉴权的 worker 完成。本地随手截图可以辅助讨论，但需要可信重放才能用于完成证书。证据机制假定 worker 主机可信，不声称能防住已被控制的主机。
- 同配置尽量可重复；跨 GPU 和浏览器版本采用显式误差容忍，不能要求所有机器字节级相同。

### B. 原图参考视角

按对象和区域分别检查位置、轮廓、投影大小、遮挡和色彩；保留整体差异图，但不用一个全局相似度放行。

首版试验门槛如下，需在独立基准上校准、冻结版本后才能作为发布标准；不是已经实测达到的效果，也不等于主观“还原了百分之多少”。

| 检查 | 初始目标 |
|---|---|
| 主要对象完整性 | 原图标注的所有关键对象均有对应对象；不允许漏建筑、漏船或用无关形状替代 |
| 关键对象中心误差 | 相对场景裁剪框对角线 ≤ 2% |
| 关键对象投影宽高误差 | 各自相对原图目标框 ≤ 8%，微小对象另设像素容忍 |
| 可可靠分割的关键对象轮廓 | 可见部分 silhouette IoU ≥ 0.85；低置信度标注转人工复核，不以排除项自动通过 |
| 遮挡关系 | 原图已标注的关键前后关系无颠倒 |
| 模型局部发现 | 每个关键对象和整体构图均有审查；不得有未解决的 blocker／major |

每条模型发现至少含 `object_id/area`、原图和捕获证据 ID、`difference`、`severity`、`planned_fix`。边界轮廓合格但屋顶样式、船壳或材质明显错误仍应阻断；数值门槛和人的视觉判断互补。

### C. 防止“原图贴在平面上就满分”

- `true_3d` 模式的主要可交互对象必须有非退化三维几何和独立变换；原图整幅投影到承载平面不能完成验收。
- 允许纹理、地面等合理平面，但要登记用途；不能仅用“三角面数很多”证明立体。
- 随机选择允许范围内的侧视角和对象移动，检查可见侧面、视差、深度、拾取和对象独立运动；执行禁用参考图投影的诊断视图。
- `billboard / projected_texture` 对象单列比例和作用范围；主要物件靠它们成立时标记 `preview_only / 2.5d`，不能签发 `true_3d` 完成证书。
- 未提供侧面参考图时，侧面测试只证明结构和交互合理，不能证明侧面忠于原图。

### D. 交互、侧视角与移动端

水乡基准至少覆盖：参考视角、左右 30°／60°（在声明范围内）、较高俯视角、桌面 1440×900、窄屏 390×844、横屏 844×390。原图对照另使用原生参考画布，不能把桌面截屏拉伸匹配原图。

真实鼠标／触摸／键盘测试：旋转与缩放、拖船不转镜头、木箱不离开台面、船不离开水道、暂停后位置稳定、继续没有大幅跳变、Esc／pointercancel 恢复、复位还原物件与视角、日暮切换、窗口缩放、触屏双指和单指冲突、焦点可见以及可替代拖动的键盘操作。声明的每个控制都必须有实际事件和结果证据，不能只提交 `passed=true`。

动画和拖动的碰撞先用代理形状与允许区域处理，明确不是通用物理引擎。验收限定在声明的视角和动作范围内，不承诺自动发现所有三维穿插。

### E. 性能与完成状态

首版暂定桌面目标中位帧率 ≥ 45 FPS、移动设备目标 ≥ 30 FPS，并记录 p95 帧时、首屏可交互时间、三角面、draw calls 和纹理内存估计。具体门槛必须绑定真实设备、分辨率、DPR 和预热后测试时长，不能用桌面浏览器模拟手机尺寸就称手机性能通过。

静态布局的移动端检查可以先做模拟；没有真实设备性能证据就标记 `mobile_performance_unverified`，不签发移动设备性能声明。首版默认至少包含一台已登记的真实桌面设备和移动布局检查；移动真机性能若为任务必需项，在建任务时就写入合同。设备范围不能在验收失败后静默缩减，修改范围要生成明确的新合同版本。每个证书列明已测设备范围，不声称覆盖所有手机。

完成条件分列 `reference_visual_pass`、`geometry_pass`、`interaction_pass`、`performance_pass_for_declared_targets`、`evidence_valid`。所有声明范围内的必需项均满足才允许 `workflow_complete=true`；明确返回 `preview_only`、未支持项和推断结构。

拟议证书：`canvaslab-3d-reference-v1` 与 `canvaslab-3d-complete-v1`，绑定同一构建和验收配置。证书仅证明规定范围内的证据通过，不代表精确数字孪生或“100% 还原”。

## 9. GPU、模型与导出策略

| 工作 | 第一版执行位置 | GPU 要求 |
|---|---|---|
| 模型看图、规划、审查 | 调用方模型 | 不要求用户本机安装推理卡；依赖调用方模型能力 |
| 配置校验、生成工程、任务保存 | MCP 服务 CPU | 不依赖 GPU |
| OCR、对象分割（可选） | 现有视觉后端或隔离 worker | 沿用现有 GPU 能力并限流；缺失时可用模型标注先完成参数化流程 |
| 实时网页与正式截图 | 浏览器／渲染 worker | 使用该机器的图形能力；软件渲染仅作兼容辅助，不能代表实际用户性能 |
| 复杂人物／动物图生模型 | 后续独立适配器 | 首版不安装；选型后测显存、模型许可、格式、耗时和质量 |

现有两张 Tesla P4 是否适合某个未来图生 3D 模型，要看单卡显存、算子、计算精度和实际测试；不能把两张卡的显存自动当作一张大卡。此规划不承诺它们能运行任何指定的新模型。

首版交付优先是完整 Three.js 网页源码 ZIP、可部署静态包、场景配置、资产清单、操作说明和审计证据。后续再支持 GLB，适用于网格、受支持材质和动画；网页按钮、拖动逻辑、JavaScript 水面 shader 不会因为导出 GLB 就自动变成通用可执行应用。需要导出降级清单及必要的动画／材质烘焙。[GLTFExporter 文档](https://threejs.org/docs/pages/GLTFExporter.html)

## 10. 版本、部署与安全

### 避免再次拿旧 MCP 测新功能

`scene_runtime_status` 和每份产物都记录：`server_version`、`git_commit`、`source_tree_digest`、`contract_version`、`generator_version`、`runtime_bundle_sha256`、`schema_digest`、worker／浏览器版本、测试配置版本和可选模型版本。

发布使用固定构建包；正式验收不使用无法追溯的脏工作区构建。每次验证先比较目标版本和在线状态，再创建任务；整个任务绑定版本，处理中服务升级不能把旧配置和新生成器混用。

独立预发布 → 单测与协议测试 → 水乡和其他基准真实生成 → 验证证据链 → 原子切换 3D 服务 → 第二台客户端读版本并跑一个小样 → 保留可回滚版本。二维服务不随本次 3D 发布重启。新增工具需要验证客户端工具发现；不承诺客户端永远不需要重连。

### 不限制用户机器 IP，但仍保留安全边界

- 不硬编码某台客户端 IP 白名单；允许有权限且网络可达的其他机器连接。
- 新服务的鉴权、来源域名配置、上传限制、任务配额与渲染沙箱从首版设计进去。Host／Origin 防护与“限制哪些客户端 IP 能访问”不是一回事，未来增加官网域名走配置。
- 对公网发布前必须具备 HTTPS 和鉴权；不把当前二维无鉴权配置直接照搬。
- 只接受登记资产，不让模型传任意 shell 命令、任意 JS、外部 npm 包或随意下载的模型地址。校验图片解码大小、路径穿越、压缩包展开体积、纹理和几何预算。
- 模型／纹理资产记录来源和使用许可；用户原图未经授权不发送给外部图生 3D 服务。
- 捕获浏览器在隔离、低权限环境运行，网络仅访问当前构建所需资产，不访问主机凭据或无关内网地址。
- 3D 任务可以先设一个并发渲染槽和一个可选 GPU 槽；实际上传／存储上限做成配置并经压测确定。排队可取消，重启返回明确中断／续跑状态，禁止无限重试。

## 11. 实施里程碑与交付门槛

| 阶段 | 交付 | 退出条件 |
|---|---|---|
| M0：锁定基准与合同 | 用户原始水乡图、独立标注、现有页面当前诊断截图、scene schema、3D 服务版本格式 | 原图能找回且有哈希；确定关键对象、可测视角、首台捕获设备和必测设备范围；二维回归基线保留；本阶段诊断截图不作为正式证书 |
| M1：最小可运行闭环 | 独立 MCP、上传／状态／校验／生成／下载；固定运行时；最小鉴权 worker 和固定截图；简单场景和水乡灰模 | 同配置生成相同规范化产物；两张不同参考图能使用同一组件库生成，不把水乡坐标写进生成器；至少一台登记设备完成捕获；图形能力缺失时明确报错 |
| M2：构图与造型还原 | 相机匹配、参数化屋顶／船／码头、局部材质与灯光 | 与原图逐对象对照；比现有水乡基线改善关键对象误差；只改参数重建，不手工修改某页源码救场 |
| M3：审计和交互闭环 | 可信多视角捕获、局部审查、拖动／动画／性能测试、有限迭代与失败报告 | 旧截图、伪 observation、整图平面、错误版本、局部严重变形均被拒绝；真场景通过声明范围内测试；校准并冻结验收配置与性能基准 |
| M4：首版发布 | 独立部署、客户端连接文档、工程包和证据报告 | 至少 5 个固定参考样本完成测试；必测设备（至少一台真实桌面设备）通过冻结的性能基准；回滚演练通过；第二台客户端真实调用；现有二维基准无新增回归 |

M1 是工程可运行，不是产品完成；M4 才是可交付 3D MCP 的首版。暂不按“几天做完”承诺，以各阶段实际证据推进。

基准建议：水乡、建筑展台、简单室内角落、低多边形小岛、产品／机械形体。全部用合法持有的固定原图，记录支持范围；另设写实人脸、密集树林等明确不支持样本，验证系统会解释限制而非假通过。

必须有负例：贴原图的平面、正面像但侧面空、只改次要纹理却漏主要物件、船拖到岸上、换构建复用旧审计、更新纹理不更新摘要、软渲染冒充真机性能、错误 job_id／过期证据、构建中取消和服务重启。

实现顺序优先 M0 → M1 → M2 → M3 → M4。后续才考虑多视图输入、图生 GLB、复杂人物动物、自动材质生成、更多程序化组件、2.5D 独立模式，以及 App／小程序适配。

## 12. 本轮交付与下一步

本轮仅新增这份规划，不改生成器、不安装模型、不修改水乡页面、不部署、不提交或推送仓库。

下一步实施的最小切片是 M0/M1：新建 `server3d` 和 `runtime3d`，先跑通“原图 → 结构化配置 → 同一运行时生成两种小场景 → 固定截图”，然后再加入水乡细节和严格审计。这样先验证它确实是一套可复用的新 MCP，再扩展效果。
